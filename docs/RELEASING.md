# Сборка и публикация релиза

Основной target `HHVacancyCBR` определяет `MARKETING_VERSION` и `CURRENT_PROJECT_VERSION`. Подтверждайте их по `Info.plist` собранного `ЦБВакансии.app`; версии тестовых targets для выпуска не используются. Текущая схема: тег `v1.3.4-15`, название `ЦБВакансии 1.3.4 (15)`, файлы `HHVacancyCBR_1.3.4_15_macos13_arm64.dmg` и `.dmg.sha256`.

## Подготовка точного коммита

Работайте по AGENTS.md. Проверьте чистоту индекса и рабочей копии, `git fetch origin --tags`, сравните main с origin/main, существующие теги и Releases. Не перемещайте опубликованные теги и не перезаписывайте вложения другим содержимым. Не повышайте версию ради обновления документации.

Выполните [обязательные проверки](TESTING.md), отправьте точный коммит и дождитесь успешного workflow `macOS` для полного SHA: `build-and-test`, `release-build`, `ui-tests`. Только после этого создавайте аннотированный тег на выбранном коммите. У аннотированного тега SHA объекта и SHA commit различаются; `git rev-parse 'v1.3.4-15^{commit}'` показывает исходный commit.

Пример для **ещё не существующего** тега (подставьте проверенный полный SHA):

```sh
release_commit=FULL_VERIFIED_COMMIT_SHA
git tag -a v1.3.4-15 "$release_commit" -m 'ЦБВакансии 1.3.4 (15): проверенный выпуск'
git push origin refs/tags/v1.3.4-15
```

## Установщик

Workflow [Release DMG](../.github/workflows/release.yml) запускается по `v*` или вручную на выбранном ref. Он вызывает [scripts/release.sh](../scripts/release.sh), экспортирующий чистый commit через `git archive`, выполняющий строгую Release-сборку, проверку подписи/entitlements и hdiutil, затем сохраняет два файла как Actions artifact `HHVacancyCBR-DMG`. Это **не** GitHub Release.

Локально на чистом выбранном коммите используется тот же сценарий:

```sh
bash scripts/release.sh --output-dir "$PWD/releases/verification"
```

Каталог должен не содержать одноимённого DMG/checksum. `scripts/publish_release.py` безопасно публикует только в локальный каталог; он не отправляет файлы в GitHub. Сценарий не устанавливает приложение. По умолчанию подпись ad hoc; Developer ID и нотарификация возможны только с реально настроенными `DEVELOPER_ID` / `NOTARY_PROFILE`.

Перед публикацией скачайте артефакт успешного Release DMG для точного SHA. Проверьте checksum, `hdiutil verify`, Info.plist (версия/build/minimum macOS), архитектуру arm64, `codesign --verify --deep --strict`, `scripts/verify_release_entitlements.py --app /path/to/ЦБВакансии.app`, hardened runtime и исходный SHA в README образа. Отсутствие Developer ID/нотарификации укажите явно. Не требуйте одинакового хеша при новой упаковке: валидируется конкретный публикуемый файл.

## GitHub Release

Подготовьте русское описание: изменения относительно предыдущего релевантного тега, требования, установка, checksum, подпись, исходный SHA, CI и ограничения. Различайте исправления надёжности, рефакторинг и документацию. Старые живые проверки не объявляйте испытанием нового бинарного файла.

Создайте draft на уже проверенном теге, загрузите DMG и `.sha256`, скачайте их обратно и сравните с локальными файлами. После проверки опубликуйте draft как стабильный Latest. Повторно проверьте видимость карточки, ссылки и загруженные байты. Исторические Releases сохраняются с явной пометкой и ссылкой на текущий стабильный выпуск; пустые карточки для каждого старого тега не нужны.

Проверка пользователем после скачивания обоих файлов в один каталог:

```sh
shasum -a 256 -c HHVacancyCBR_1.3.4_15_macos13_arm64.dmg.sha256
```

Ожидается `OK`. Бинарные файлы не добавляйте в Git. Изменение видимости репозитория, доступов, лицензии и существующих тегов не относится к обычной публикации выпуска.
