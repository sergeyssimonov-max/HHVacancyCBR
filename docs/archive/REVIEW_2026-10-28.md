# Рецензия на доработку и отладку ЦБВакансии 1.1 (5)

Дата: 28.10.2026. Объект: ветка `main` на коммите `26105b8`, весь репозиторий (около 16 400 строк, из них 4 528 – тесты).

Метод: построчное чтение всего Swift-кода приложения, тестов, CI, скриптов выпуска и документации. На Linux прогнаны Python-тесты, `verify_independence.py` и сверка Streebog с эталонными векторами. Swift toolchain в среде аудита нет, поэтому выводы по Swift получены из чтения кода, без запуска. Места, где факт требует проверки на Mac или в документации hh.ru, помечены «требует проверки».

## Итог

Сетевой слой, отмена операций и запись PDF без перезаписи сделаны тщательно, это не черновик. Продукт мешают назвать отполированным три системные проблемы:

1. Секрет и доказательная часть. Токен hh.ru лежит открытым текстом в Git и в каждом DMG. Архив «исходных ответов» растет без предела, стоит на критическом пути каждого запроса и при повреждении блокирует экспорт PDF. При этом обещание «хеш подтверждает неизменность» юридически ничего не доказывает.
2. Производительность. Классификатор полевых учреждений с десятками регулярных выражений запускается при каждом создании `VacancySearchResult`, то есть при каждом рендере избранного и каждом обновлении статуса. Полный снимок вакансий пишется на диск в главном потоке при каждом открытии описания.
3. Продуктовая недоделка. В приложении для поиска вакансий нет поиска по тексту и выбора сортировки. Ссылки в описании вакансии не открываются. Кнопка экспорта PDF в карточке после первого успеха блокируется навсегда.

Шкала приоритетов: P0 – исправить до следующего выпуска, P1 – до версии 1.2, P2 – полировка, P3 – по возможности.

## P0. Блокеры выпуска

### P0-1. Токен hh.ru в Git и в бинарнике

`HHVacancyCBR/HHAuthConfig.swift:5` – application token длиной 64 символа хранится открытым текстом с первого коммита `cc18fdf`. README фиксирует это как решение владельца. Репозиторий приватный, но DMG раздается как артефакт GitHub Actions, и токен извлекается из бинарника командой `strings`. Каждый получатель DMG получает токен приложения и может исчерпать его квоты или вызвать блокировку от имени владельца.

Что сделать:

- проверить, нужен ли токен вообще: публичный поиск `GET /vacancies` и `GET /vacancies/{id}` исторически работал без авторизации, при обязательном `HH-User-Agent` (требует проверки по текущим правилам hh.ru). Если не нужен – удалить авторизацию целиком;
- если нужен – перенести в Keychain с вводом при первом запуске или в `.xcconfig`, исключенный из Git, и подставлять в CI из секрета;
- перевыпустить токен в кабинете разработчика hh.ru: старый навсегда остался в истории Git;
- удалить тест `testEmbeddedApplicationTokenIsConfigured` (`HHVacancyCBRTests.swift:176`), который закрепляет секрет в исходниках, и соответствующую проверку в `verify_independence.py`.

### P0-2. Архив исходных ответов на критическом пути запроса

`HHAPIClient.swift`, функция `data(for:)`: после каждого успешного ответа выполняется `try PDFSourceEvidence.shared.capture(...)` – синхронный разбор JSON, хеш Streebog и запись двух файлов, внутри общего `HHRequestGate`. Последствия:

- переполненный диск, отказ прав или любой сбой записи превращает успешный ответ hh.ru в ошибку запроса. Сбор вакансий ломается из-за подсистемы, которая нужна только PDF;
- сетевой клиент знает про PDF (`PDFSourceError` бросается из API-клиента) – нарушение слоев и глобальное состояние через `.shared`;
- дисковый ввод-вывод и хеширование задерживают очередь запросов.

Исправление: `capture` вызывать вне гейта, ошибки записи логировать и превращать в `observationID = nil`, а не в отказ запроса. Зависимость передавать через протокол в инициализаторе клиента, без синглтона.

### P0-3. Неограниченный рост `documented-archive-v1`

Каждая страница каждого обновления (до 2 000 запросов за сбор, по 100 вакансий в ответе) записывается навсегда. Политики хранения нет, UI архива удален в 1.1 (4), документация прямо говорит «автоматически не удаляются». За месяц ежедневных обновлений это сотни мегабайт в контейнере, о которых пользователь не знает.

Исправление: хранить только наблюдения, на которые ссылаются избранное и текущий снимок. Остальное удалять после успешного сохранения нового снимка. Добавить в README размер и способ очистки.

### P0-4. Пропавшее наблюдение навсегда ломает экспорт PDF

`PDFSourceEvidence.materials(for:)` бросает ошибку, если файл наблюдения отсутствует или не сходится хеш. Избранное хранит `observationID` бессрочно. Пользователь, удаливший архив ради места (см. P0-3), больше не сможет выгрузить ни избранное, ни карточку: `exportVacancyPDF` к тому же глушит причину до «Не удалось сохранить PDF.» (`VacancySearchViewModel.swift:743`).

Исправление: отсутствующее наблюдение – предупреждение в документе («исходный ответ не сохранился»), а не отказ. Расхождение хеша – заметная пометка в PDF. В `exportVacancyPDF` показывать `error.localizedDescription`.

### P0-5. Падение на дубликатах в избранном

`VacancySearchViewModel.swift:353`: `Dictionary(uniqueKeysWithValues: favorites.map { ... })` аварийно завершает процесс при двух записях с одним `id`. `FavoriteVacancyStore.load()` дубликаты не проверяет, в отличие от `VacancySnapshotStore.load()`. Файл, поправленный вручную или восстановленный из резервной копии, роняет приложение при первом обновлении. Тот же паттерн – строки 245 и 352.

Исправление: проверка уникальности при загрузке плюс `Dictionary(_:uniquingKeysWith:)` во всех трех местах.

### P0-6. Доказательная сила PDF завышена

`docs/DOCUMENTED_PDF.md`: «Совпадение хеша при повторном расчете подтверждает неизменность приложенных исходных байтов». Хеш и байты создает и хранит одна сторона в одном файле, без подписи и без доверенной метки времени. Любой, кто изменит вложение, пересчитает и хеш. Совпадение подтверждает только внутреннюю согласованность файла, но не происхождение данных от hh.ru и не время получения. Для пользователя, который может предъявить такой PDF в споре, это опасная формулировка.

Исправление на выбор:

- честная формулировка: «контрольная сумма для обнаружения случайных повреждений, не является доказательством происхождения»;
- или настоящая фиксация: метка времени по RFC 3161 от внешнего TSA и подпись документа (усиленная электронная подпись по Федеральному закону от 06.04.2011 № 63-ФЗ «Об электронной подписи»). Это отдельный проект, оценивать до начала работ.

## P1. Ошибки и производительность

### P1-1. Классификатор в конструкторе модели

`HHModels.swift:729`: `VacancySearchResult.init` всегда вызывает `FieldInstitutionClassifier.classify`. Тот режет полное описание на предложения и для каждого прогоняет до 25 регулярных выражений, которые `String.range(of:options: .regularExpression)` компилирует заново при каждом вызове. Конструктор вызывают:

- `updatingArchiveStatus`, `updatingDetailState` – при каждом изменении состояния карточки;
- `FavoriteVacancyRecord.searchResult` – внутри `unfilteredResults`, то есть на каждом рендере режима «Избранное»;
- загрузка снимка и каждое обновление.

Исправление: классифицировать один раз при получении данных, хранить результат и копировать его в `updating*`. Регулярные выражения скомпилировать один раз как статические `NSRegularExpression`.

### P1-2. Многократный пересчет `displayedResults` в одном кадре

`displayedResults` – вычисляемое свойство с фильтрацией и сортировкой. `MainWindow` обращается к нему до шести раз за один `body` (условия `content`, два счетчика в `statusBar`, `results`), плюс `reconcileExpanded` и `normalizeFilters`. В режиме «Избранное» каждое обращение пересобирает все записи (см. P1-1) и сортирует их с разбором дат. `isFavorite(id:)` – линейный поиск на каждую строку, итог O(n²) на рендер.

Исправление: `@Published private(set) var displayedResults`, пересчитываемый при изменении `results`, `favorites` или фильтров. `Set<String>` идентификаторов избранного.

### P1-3. Запись снимка в главном потоке при открытии описания

`VacancySearchViewModel.swift:546`: `apply(details:)` синхронно кодирует и пишет весь `vacancies.json` (тысячи вакансий) на главном акторе при каждом раскрытии карточки. Ошибка записи подменяется неточным текстом «Не удалось сохранить уточненную категорию вакансии». Загрузка всех хранилищ в `loadPersistenceIfNeeded` и справочника регионов тоже идет на главном акторе.

Исправление: отложенное сохранение (debounce 1–2 секунды) в фоновом `Task.detached`, как уже сделано для избранного.

### P1-4. Разбиение по датам не учитывает округление hh.ru

По документации hh.ru `date_from` и `date_to` округляются вниз до 5 минут. `collectByDate` делит интервал пополам до 300 секунд без выравнивания: середины не попадают на границы, часть запросов дублируется, а на последнем уровне `date_from` и `date_to` округляются в одно значение. Формат `ISO8601DateFormatter` по умолчанию дает суффикс `Z`, а документация описывает `±hhmm` (поведение с `Z` требует проверки).

Исправление: выравнивать границы и середину на 5 минут, минимальный интервал – 5 минут, формат даты – `yyyy-MM-dd'T'HH:mm:ssZ`.

### P1-5. Устаревший параметр `schedule`

hh.ru объявил `schedule` устаревшим в пользу `work_format`, `working_hours` и смежных справочников. Разбиение по словарям (`collectByDictionaries`) и определение удаленной работы (`AreaDirectoryIndex.location`, `summary.schedule?.id == "remote"`) на него опираются. Пока параметр принимается, но удаление сломает последний уровень разбиения молча.

Исправление: заменить третье измерение на `working_hours`, проверку удаленки оставить только по `work_format`.

### P1-6. Вакансии с несколькими регионами и удаленные теряют регион

`AreaDirectoryIndex.location`: при `areas.count > 1` результат – «Регион не определен», хотя основной `area` известен. Признак `REMOTE` в `work_format` полностью заменяет регион, и удаленную вакансию Банка России из Москвы нельзя найти фильтром «Москва».

Исправление: регион брать из `area` всегда, удаленность хранить отдельным признаком и показывать меткой.

### P1-7. Неполное обновление выбрасывается целиком

`performSearch`, строки 359–364: если новый сбор неполный, а прежний был полным, новые данные отбрасываются без сохранения, сколько бы дней ни было прежнему снимку. После недели блокировок пользователь видит недельные вакансии с пометкой «полная выборка».

Исправление: при возрасте прежнего снимка больше суток показывать новые неполные данные или объединение с пометкой, а в предупреждении писать возраст снимка.

### P1-8. Двойной разбор HTML-сущностей

`HHModels.swift:866–871`: `&amp;` декодируется первым, поэтому `&amp;lt;` превращается в `<`, а не в `&lt;`. Не поддерживаются `&laquo;`, `&raquo;`, `&mdash;`, `&ndash;` и числовые `&#...;`, и они попадают в сниппеты, классификатор и PDF как есть.

Исправление: `&amp;` декодировать последним, остальные сущности – через `CFXMLCreateStringByUnescapingEntities` или таблицу.

### P1-9. Ложноположительная классификация «залипает»

`HHModels.swift:730`: если сохраненная оценка – «полевое учреждение», а новая классификация по полному описанию дает «нет», остается старая. `FavoriteVacancyRecord.update` тоже обновляет оценку только в положительную сторону. Исправленная ошибка классификатора не исправит уже сохраненные данные.

Исправление: решение по полному описанию (`isDetailLoaded`) всегда приоритетнее сохраненного. Хранить версию классификатора и переоценивать при ее смене.

### P1-10. Встроенный список работодателей не обновляется

`EmployerConfigurationStore.loadOrCreate`: встроенный `employers.json` копируется только при первом запуске. Новая версия приложения с дополненным реестром не дойдет до существующих пользователей никогда.

Исправление: версия реестра в файле и слияние при обновлении (добавлять новые встроенные записи, не трогать пользовательские), либо разделить встроенный и пользовательский списки.

### P1-11. Миграция избранного может сделать его нечитаемым

`FavoriteVacancyStore.load()`, строка 227: при версии 1 вызывается `save` внутри `load`. Сбой записи (диск полон) выбрасывает ошибку из `load`, и полностью читаемое избранное объявляется поврежденным, а запись блокируется до перезапуска.

Исправление: вернуть данные, а миграционную запись выполнить отдельно, с предупреждением при сбое.

### P1-12. Нет пути восстановления из поврежденных файлов

Поврежденный `favorites.json` или `vacancies.json` дает предупреждение и блокировку записи, но пользователь не может ничего сделать без ручного удаления файла внутри `~/Library/Containers`. Исправление: переименовать поврежденный файл в `*.corrupted-<дата>.json`, начать с чистого состояния и сообщить, где лежит копия.

### P1-13. HTML описания импортируется WebKit на главном потоке

`NSAttributedString(data:options:.html)` выполняется на главном акторе для каждой вакансии экспорта. Импорт HTML крутит вложенный run loop, и во время экспорта SwiftUI может обработать нажатия и изменения модели (повторный вход). Для 100 вакансий интерфейс заметно подвисает.

Исправление: свой конвертер узкого подмножества тегов, которое и так оставляет `sanitize`, без WebKit, в фоновом акторе.

### P1-14. Сообщения об ошибках hh.ru

- `rateLimited(retryAfterSeconds: header.flatMap(Int.init))` теряет значение, если `Retry-After` передан датой.
- `requestFailed` показывает только код и прячет `description` из ответа.
- Статус прогресса выводит пользователю `area=113, date, experience=between1And3` – отладочную строку. Нужны человеческие подписи: «Москва», «по датам публикации».

## P2. Продукт и интерфейс

1. Поиск по тексту в названии и описании и выбор сортировки: по дате, по зарплате, по работодателю. README обещает «фильтры и сортировку», сортировка сейчас одна и фиксирована.
2. Ссылки в описании: `Coordinator.decidePolicyFor` отменяет любую навигацию, кроме `about:`, и клик по ссылке ничего не делает. Нужно открывать `http(s)` через `NSWorkspace` и возвращать `.cancel`.
3. Высота описания: `WKWebView` с `minHeight: 320` внутри `ScrollView` дает вложенную прокрутку и пустоты под коротким текстом. Нужно измерять `document.body.scrollHeight` или показывать текст через `Text(AttributedString)`.
4. Кнопка «Экспорт в PDF» в карточке после успеха получает `.disabled(exported)` и больше не работает. Нужно сбрасывать метку через 2 секунды, как у «Скопировано».
5. Экспорт избранного сначала полностью готовит документ (сеть, импорт HTML, разметка) и только потом спрашивает каталог. Отказ в диалоге выбрасывает всю работу. Карточка и статистика спрашивают путь сначала. Нужен один порядок: сначала путь.
6. Нет меню и сочетаний клавиш: ⌘R – обновить, ⌘F – поиск, ⌘E – экспорт, Esc – отмена загрузки.
7. Кнопки с символами «★ ☆ ✓ ↗» вместо SF Symbols, нет `accessibilityLabel` у иконочных состояний.
8. Зарплата: дефис вместо среднего тире (`150 000-220 000`), обычный пробел-разделитель тысяч (в PDF число разрывается переносом), «руб.» и сырые коды валют (`USD`, `KZT`). Нужны `–`, неразрывный пробел и человеческие названия валют. То же для «язык - уровень» в PDF (`FavoriteVacanciesPDFExporter.swift`, раздел «Языки»).
9. Буква ё в интерфейсе используется непоследовательно: «Удалённо», «отчёт», «подтверждённых» рядом с «Еще работодателей». Выбрать одно правило и прогнать по всем строкам.
10. Тексты интерфейса зашиты в код. Для будущей локализации и единой вычитки вынести их в `Localizable.xcstrings`.

## P2. Код и архитектура

1. `HHAPIClient.get`: принудительные приведения `as! T` для подстановки `observationID` по типу. Нужен отдельный путь для двух типов или протокол `ObservationStamped`.
2. `request.url!` в горячем пути, `ISO8601DateFormatter` и `DateFormatter` создаются на каждый запрос и каждое форматирование даты (`timeMessage`, `publicationDate`, `PDFFileNameBuilder.timestamp`).
3. `User-Agent: HHVacancyCBR/1.0` при версии 1.1. Брать из `CFBundleShortVersionString`.
4. `VacancyCollectionService`: комментарий про «47 employers × 20 pages» и лимит 2 000 запросов унаследованы от СберВакансий. Для четырех работодателей бюджет нужно пересчитать и задокументировать.
5. Заголовок `Created by Codex on 05.07.2026` в `HHModels.swift` – единственный файл с таким заголовком, и дата раньше создания проекта.
6. `VacancySearchViewModel` – 892 строки и десять зон ответственности: поиск, детали, избранное, архивные проверки, три вида экспорта, панели AppKit. `NSSavePanel` в модели делает экспорт карточки нетестируемым (для статистики выбор пути уже внедряется). Разделить на `SearchController`, `FavoritesController`, `ExportController`.
7. `PDFExportWorker.prepare` размечает каждую вакансию дважды: оценка страниц и итоговая разметка.
8. `PDFOriginalMaterials.embed` правит PDF регулярными выражениями. Словарь каталога ищется ленивым `<<[\s\S]*?>>`, и вложенный словарь в каталоге обрежет его. На выходе CoreGraphics сейчас это работает, но защиты от смены формата нет, кроме проверки после записи. Нужен тест на каталог с вложенным словарем и `/Subtype /application#2Fjson` у вложений.
9. Реестр полевых учреждений содержит пять-значные номера (`10513`, `25631` и другие) без ссылки на источник каждого. Происхождение номеров требует проверки, ложное срабатывание по случайному числу в тексте возможно.

## P2. CI и выпуск

1. Действия закреплены тегами (`@v4`, `@v5`), а не SHA. Нет блока `permissions:` – токен GitHub с правами по умолчанию. `persist-credentials` не отключен.
